    少しずつ波形化すれば VOICEVOX と同様の真のストリーミングが可能。

--------------------------------------------------
方針(予定)
--------------------------------------------------
1. AIVMX を前段/デコーダの2つの ONNX に分割(onnx.utils.Extractor)し、出力一致を検証
2. デコーダの受容野からのりしろ量を決め、区間デコードが一括デコードと一致することを検証
3. 長文は文単位でも分割し、BERT/前段の処理時間も先頭文だけで済むようパイプライン化
4. エンジン(FastAPI 等)に依存しない最小コア (transformers 不要のトークナイザ自前実装など)
5. VSU を参考に NVDA synthDriver を作成し、最初の音が出るまでの時間を計測

03:23-03:36 遅延の内訳調査と高速化
--------------------------------------------------
- scripts/profile_latency.py : 文長ごとに g2p / BERT / front / 最初の dec の時間を計測。
  測るたびに 2〜4 倍ばらつく現象があり、原因を 3 つ特定した。

  (1) ORT の arena_extend_strategy=kSameAsRequested (AivisSpeech Engine の設定をそのまま使っていた)
      scripts/prof_front.py (ORT プロファイラ) : カーネル時間 307ms に対し実時間 1050ms。
      scripts/bench_front2.py : 800 フレームの front が kSameAsRequested 1015ms → 既定アリーナ 236ms。
      アリーナ無効 492ms、ORT 既定 (全スレッド+スピン) 295ms、最適化レベルはほぼ無関係。
      → 既定アリーナに変更、最適化レベル EXTENDED。
      ※ 本家 AivisSpeech Engine 自体が遅い原因の一つと思われる。

  (2) Windows 11 の電力スロットリング (EcoQoS)。バックグラウンドのプロセスが E コア/低クロックに寄せられる。
      aivis_core/winperf.py で SetProcessInformation(ProcessPowerThrottling) を制御して比較:
        強制 ON : 5文字 703ms / 40文字 1510ms / 80文字 2761ms (最初の音まで)
        強制 OFF: 5文字 216ms / 40文字  350ms / 80文字  827ms
      NVDA は常にバックグラウンドプロセスなのでまさにこれに該当する。
      → AivisCore 初期化時にプロセスの実行速度スロットリングを無効化 (disable_power_throttling=True)。

  (3) BERT の fp16 モデルは CPU では遅い (Cast だらけ)。scripts/bench_bert.py:
        fp16: 5 トークン 122ms / 74 トークン 166ms
        fp32:            40ms /             82ms   特徴量 cos=1.0000 (同一)
        int8 (動的量子化):22ms /             51ms   cos≈0.96〜0.98 (特徴量が変わるので不採用)
      → fp16 モデルをロード時にメモリ上で fp32 に変換 (bert_models.fp16_model_to_fp32)。
        model.onnx (fp32) があればそれを使う。メモリは 650MB → 1.3GB に増える。

- その他の調整
  - 前段 (flow) は文長に超線形 (80 文字=1200 フレームで約 0.6 秒)。
    → 先頭の文は 30 文字を超えたら読点で区切る、80 文字超の文も読点で区切る (StreamConfig)。
  - 先頭区間が無音でトリムされると次の 64 フレームを待つことになっていた → 区間長を 16→32→64 と段階的に。
  - margin を 12 フレームに (検証で一括と同一になる最小値)。
  - 音量: 固定ゲイン 2.4 倍 + |y|>0.85 でソフトクリップ (本家のピーク正規化はストリーミング不可のため)。
  - DirectML (GPU) は新しい入力形状ごとのオーバーヘッドが大きく、短い発話ではむしろ遅い
    (最初の音まで中央値 484ms)。→ 既定は CPU。

- scripts/bench_nvda.py + scripts/nvda_texts.txt : NVDA で読まれがちな 30 種の異なる発話で計測 (CPU)
    当初 (kSameAsRequested, fp16)  : 計測不安定 (中央値 500ms〜)
    アリーナ修正+スロットリング無効: 最初の音まで 中央値 250ms / p90 334ms

    BERT: CPU 47ms → CUDA 8ms / 前段: CPU 43ms ← CUDA 121ms (遅い) / デコーダ RTF: CPU 0.12 → CUDA 0.05
  → BERT とデコーダは GPU、前段は CPU に分けるのが最良。最初の音まで CPU 138ms → 分割 CUDA 90ms、
    CPU 使用時間 (音声 1 秒あたり) 0.15 秒 → 0.01〜0.04 秒。

    DEFAULT の方が速い (最初の音 90ms 対 123ms)。DEFAULT のまま。
  - DirectML も同じ分割にすると改善 (前段 220ms → CPU 52ms) するが、CUDA には及ばない。

  必要な DLL は実測で絞った: cublas, cublasLt, cufft, cudart, cuDNN 7 個 (cudnn_adv = RNN 用は不要)。
  curand / nvrtc / nvJitLink / TensorRT プロバイダは不要。
  本体側: paths.find_cuda_pack() (addons\aivisCudaPack\cuda か 設定フォルダ\aivis\cuda)。見つかれば
  sys.path の先頭に置いてパックの onnxruntime を使い、GPU を使う設定なら CUDA の DLL を先に読み込む。
  読み込みに失敗したら同梱の onnxruntime に戻す。パックが無ければ従来どおり (ハーネスで確認済み、変化なし)。

    連打の中央値 144ms (CPU 201ms)、5 倍の連続読み 最初の音 137〜144ms・音切れ 0、
    短いテキストの連続 (メニュー項目) も 3.6〜4 倍で音切れ 0 (CPU では項目間に 10〜90ms)。
  ただし、しばらく (2 秒以上) 何も読まなかった後の最初の発話が遅い: 250〜390ms (CPU は約 190ms)。
- 遅くなる原因の調査 (scripts/trace_cuda_short.py: 推論呼び出しごとの時間):
  - 待機 0.5 秒以内: BERT 8ms, デコーダ 1 区間 37ms。待機 2〜5 秒後: BERT 90ms, デコーダ 100〜160ms。
  - 「Conv running in Fallback mode」の警告が大量に出る。cuDNN 9.5/9.8/9.10/9.13 でも同じ
    (新しいほどデコーダはむしろ遅い: 9.10 以降 約 100ms/区間)。ORT がこのモデルの 1 次元畳み込みに
    cuDNN の新しい API を使えないためで、バージョンでは直らない。→ 9.1 のまま。
  - GPU を小さな処理で回し続けて (50ms / 200ms ごと) クロックを保つ案 → 改善せず。
    デコーダは GPU の計算そのものより、CPU 側から大量の小さな処理を GPU に送る部分が律速で、
    待機後は CPU 側の立ち上がりも遅いと考えられる。
- 結論 (現時点): CUDA は「連続して読む」場面 (連続読み・高速・連打) と CPU 負荷の削減には大きく効くが、
  スクリーンリーダーで一番多い「しばらく黙っていた後の 1 発話目」は CPU より遅い。パックも 2.1GB と大きい。
  次の案: 1 発話目の最初の区間だけ CPU で作り (BERT もこの間は CPU)、2 区間目以降を GPU に回す。
